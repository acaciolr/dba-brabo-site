Conceito

A imagem oficial mysql:8.0 empacota o servidor e um script de inicialização: na primeira subida com o diretório de dados vazio, ela cria o data directory, define a senha do root a partir de MYSQL_ROOT_PASSWORD, cria o banco de MYSQL_DATABASE e o usuário de MYSQL_USER/MYSQL_PASSWORD. O dado só sobrevive ao container se o /var/lib/mysql estiver montado num volume Docker ou bind mount — sem volume, docker rm apaga o banco junto. A porta 3306 do container é publicada no host com -p, e o healthcheck interno diz quando o MySQL aceita conexão de verdade, não apenas quando o processo subiu.

Como funciona

  • Você cria um volume nomeado (docker volume create) e sobe o container com -v apontando para /var/lib/mysql e -e MYSQL_ROOT_PASSWORD definida — sem essa variável o container recusa subir.
  • Na primeira inicialização o entrypoint inicializa o data directory, aplica as variáveis de ambiente e deixa o MySQL escutando em 3306 dentro da rede do container.
  • A flag -p 3306:3306 publica a porta no host; sem ela, só containers da mesma rede alcançam o banco.
  • O healthcheck (mysqladmin ping) marca o container como healthy quando aceita conexão — é o sinal correto para liberar a aplicação, não o estado running.
  • Parar e remover o container não toca no volume: subir um novo container com o mesmo volume devolve o banco intacto.

Na prática

  • Fixar a tag da imagem (mysql:8.0.36, não mysql:latest) para o lab ser reproduzível entre máquinas.
  • Criar o volume antes do container e dar nome explícito (mysql-lab-data) em vez de volume anônimo.
  • Guardar a senha fora da linha de comando — arquivo .env lido pelo Compose ou variável de ambiente da sessão, nunca no histórico do terminal em máquina compartilhada.
  • Criar schema e tabela de teste logo após subir, reiniciar o container e conferir que o dado continua lá — é o teste de persistência.
  • Mapear apenas a porta necessária e documentar usuário, senha e porta no README do lab.

Troubleshooting

SintomaO container sobe e sai em segundos, em loop de restart.
CausaQuase sempre MYSQL_ROOT_PASSWORD ausente, ou um my.cnf montado com sintaxe inválida.
AçãoLer docker logs mysql-lab antes de qualquer coisa — a mensagem de erro do entrypoint diz exatamente o que faltou. Corrigir a variável ou o arquivo e recriar o container.
SintomaPermission denied no /var/lib/mysql ao usar bind mount.
CausaO diretório do host pertence a outro UID; o mysqld dentro do container roda como usuário mysql (UID 999).
AçãoPreferir volume nomeado, que o Docker cria com o dono certo. Se precisar de bind mount, ajustar o dono do diretório no host para 999:999.
SintomaAplicação não conecta: connection refused na porta 3306.
CausaPorta não publicada, ou tentativa de conexão antes do healthy.
AçãoConferir docker ps (a coluna PORTS mostra o mapeamento) e docker inspect --format do health. Só apontar a aplicação depois de healthy.
SintomaO banco 'sumiu' após docker rm.
CausaO container usava o filesystem interno ou um volume anônimo que foi removido junto.
AçãoRecriar do jeito certo com volume nomeado e restaurar do backup. Volume anônimo não é estratégia de persistência — é acidente esperando acontecer.

Conceito

O Compose descreve os dois nós num único arquivo YAML: o serviço db01 como source e o db02 como réplica, ambos na mesma rede bridge criada pelo Compose, onde cada serviço resolve pelo próprio nome via DNS interno. Cada um ganha server_id próprio e GTID habilitado por arquivo de configuração montado, porque replicação exige identidade única e posicionamento global. O source cria o usuário de replicação; a réplica aponta com CHANGE REPLICATION SOURCE TO usando SOURCE_HOST='db01' — o nome do serviço, não um IP — e SOURCE_AUTO_POSITION=1, dispensando arquivo e posição.

Como funciona

  • O compose.yaml define db01 e db02 com a mesma imagem fixada, volumes separados, e monta um my-source.cnf e um my-replica.cnf com server_id distintos e gtid_mode=ON.
  • docker compose up -d sobe a rede, os volumes e os dois containers; o DNS interno resolve db01 e db02 sem IP fixo.
  • No source você cria o usuário repl com REPLICATION SLAVE restrito à rede do Compose.
  • Na réplica, um único CHANGE REPLICATION SOURCE TO com SOURCE_AUTO_POSITION=1 seguido de START REPLICA inicia o fluxo pelo GTID.
  • SHOW REPLICA STATUS na réplica e a comparação de gtid_executed entre os nós provam que a replicação anda; derrubar e recriar um container com o mesmo volume prova a persistência.

Na prática

  • Usar imagens e senhas idênticas nos dois serviços, mudando só server_id, volumes e portas publicadas (3306 para o source, 3307 para a réplica).
  • Manter os .cnf em arquivos versionados na pasta do lab — nada de docker exec para editar configuração.
  • Subir com docker compose up -d e só configurar a replicação depois de ambos healthy.
  • Escrever uma linha no source e ler na réplica como teste de fumaça de todo exercício.
  • Derrubar tudo com docker compose down (sem -v) para provar que o lab volta com os dados; usar down -v só quando quiser recomeçar do zero.

Troubleshooting

SintomaRéplica com Last_IO_Error: connection refused a db01.
CausaNome de host errado no CHANGE, ou tentativa antes do source estar healthy.
AçãoTestar do container da réplica: docker exec -it mysql-replica mysqladmin -h db01 -u repl -p ping. Se falhar, conferir nomes de serviço no compose.yaml e aguardar o healthy do source.
SintomaERROR 1236: source purged binary logs containing GTIDs.
CausaA réplica pediu GTIDs que o source já purgou — retenção curta ou réplica recriada do zero apontando para um source antigo.
AçãoReconstruir a réplica a partir dos dados atuais do source (dump com --set-gtid-purged ou clone) em vez de tentar 'pular' — o intervalo purgado não volta.
SintomaOs dois nós têm o mesmo server_id ou o mesmo UUID.
CausaCópia do volume ou do auto.cnf de um nó para o outro.
AçãoNunca clonar volume entre nós sem apagar auto.cnf. Recriar o volume da réplica e reprovisionar a partir do source.

Conceito

Backup lógico com mysqldump continua sendo a ferramenta mais didática: com --single-transaction ele tira um snapshot consistente de tabelas InnoDB sem travar escrita, e com --set-gtid-purged=ON registra no dump o conjunto de GTIDs correspondente, o que permite reconstruir uma réplica apontando para o ponto certo. O restore é um container novo com volume vazio recebendo o dump pela porta publicada. O upgrade de minor (8.0.x para 8.0.y) na imagem oficial é trocar a tag e recriar o container sobre o mesmo volume — o servidor detecta o data directory existente e executa o upgrade automático na subida.

Como funciona

  • O mysqldump roda do host contra a porta publicada, com --single-transaction e --routines --events para levar rotinas e agendadores junto.
  • O arquivo gerado contém o SET de GTID_PURGED no cabeçalho; guardá-lo junto do dump documenta de qual ponto aquele backup partiu.
  • O restore sobe um container limpo (volume novo) e injeta o dump com mysql < backup.sql — se o dump tem GTID, a instância restaurada já nasce com o gtid_executed correspondente.
  • O upgrade de minor é docker compose pull + recriar o serviço com a nova tag mantendo o volume; o log da subida mostra o upgrade do dicionário de dados.
  • Major upgrade (8.0 para 9.x) não entra nesse fluxo: exige dump + restore ou utilitário de upgrade com checagem prévia — tratar como migração, não como troca de tag.

Na prática

  • Agendar o dump por cron no host com data no nome do arquivo e retenção explícita (ex.: 7 dias).
  • Testar o restore num container separado antes de declarar que 'tem backup' — backup não testado é promessa.
  • Versionar o compose.yaml e os .cnf no git para o lab inteiro ser reconstruível.
  • Fazer upgrade primeiro na réplica, observar, e só depois no source — a mesma disciplina de produção, em miniatura.
  • Medir o tempo do restore: é o RTO do lab, e o número que decide entre dump e backup físico quando o banco crescer.

Troubleshooting

SintomaRestore falha com erro de GTID_PURGED já executado.
CausaTentativa de importar um dump com GTID num servidor que já tem aquele conjunto ou um conjunto divergente.
AçãoRestaurar sempre em volume vazio. Se precisar importar num servidor existente, regenerar o dump com --set-gtid-purged=OFF e assumir a reconciliação manual.
SintomaDump trava ou demora horas.
CausaTabela MyISAM no meio (quebra o --single-transaction) ou banco grande demais para dump lógico.
AçãoMapear engines com SELECT TABLE_SCHEMA, ENGINE, COUNT(*) ... GROUP BY; para MyISAM, aceitar o lock ou migrar para InnoDB. Para banco grande, o aprendizado aqui é o limite do dump — e a deixa para estudar XtraBackup.
SintomaApós trocar a tag, o container não sobe.
CausaPulo de major version ou variável removida na nova imagem.
AçãoLer o docker logs — o servidor diz qual parâmetro rejeitou. Voltar a tag anterior (o volume continua intacto) e planejar o upgrade como migração.

Conceito

O Vagrant descreve a VM num Vagrantfile versionado: box base (ubuntu/jammy64), hostname, rede privada com IP fixo e provisionadores shell que rodam apt install e configuram o MySQL a cada vagrant up. Diferente do container, aqui existe um sistema operacional completo com systemd — o MySQL roda como serviço, com data directory em /var/lib/mysql dentro do disco da VM. Destruir e recriar a VM a partir do mesmo Vagrantfile prova que a instalação é código, não memória de quem digitou os comandos uma vez.

Como funciona

  • O Vagrantfile fixa a box e o IP privado (ex.: 192.168.56.11), evitando DHCP aleatório que quebraria a replicação no tópico seguinte.
  • O provisionador shell atualiza o apt, instala mysql-server 8.0, ajusta bind-address e cria banco e usuário de lab via mysql já como root local.
  • vagrant up cria a VM no VirtualBox, executa o provisionamento e deixa o MySQL escutando na rede privada.
  • vagrant ssh abre o terminal da VM; do host, mysql -h 192.168.56.11 conecta pela rede privada.
  • vagrant halt desliga, vagrant up religa com os dados, vagrant destroy apaga tudo — o Vagrantfile continua sendo a única fonte da verdade.

Na prática

  • Fixar a versão da box (config.vm.box_version) para o lab não mudar sozinho num update.
  • Deixar o script de provision idempotente: CREATE USER IF NOT EXISTS, CREATE DATABASE IF NOT EXISTS — rodar vagrant provision duas vezes não pode quebrar.
  • Reservar memória e CPU explícitos no provider (2 GB / 2 vCPU é o mínimo confortável para MySQL 8.0).
  • Nunca editar configuração dentro da VM sem levar de volta para o script — o que não está no provision não existe.
  • Commits pequenos no Vagrantfile + provision.sh: cada mudança, um vagrant provision para validar.

Troubleshooting

Sintomavagrant up falha baixando a box ou criando a VM.
CausaVirtualBox desatualizado em relação ao Vagrant, ou rede do host bloqueando o download.
AçãoConferir vagrant --version e a versão do VirtualBox (a compatibilidade é estrita), e testar o download da box com vagrant box add --insecure separado do up.
SintomaHost não alcança o MySQL no IP privado.
Causabind-address ainda 127.0.0.1, ou firewall/skip-networking.
AçãoDentro da VM: SELECT @@bind_address; e ss -ltn | grep 3306. Ajustar bind-address para 0.0.0.0 no provision e criar o usuário com host % ou o IP do host.
SintomaProvision falha na segunda execução.
CausaScript não idempotente: CREATE USER sem IF NOT EXISTS aborta e o Vagrant marca o provision como falho.
AçãoReescrever com cláusulas IF NOT EXISTS e testar com vagrant provision repetido antes de declarar pronto.

Conceito

Um Vagrantfile multi-machine define db01 (192.168.56.11) e db02 (192.168.56.12) com o mesmo box e provisionadores parametrizados por papel: o source recebe server_id=1 e cria o usuário repl; a réplica recebe server_id=2 com GTID e super_read_only. IPs fixos na mesma rede privada dispensam DNS e espelham o que acontece entre dois servidores físicos. A replicação é a mesma do Compose — CHANGE REPLICATION SOURCE TO com SOURCE_AUTO_POSITION=1 — mas agora atravessando VMs completas, com systemd, logs em /var/log/mysql e latência de rede real entre nós.

Como funciona

  • O Vagrantfile declara config.vm.define para cada nó, cada um com IP privado próprio e o mesmo script de provision recebendo ROLE e SERVER_ID por variável de ambiente.
  • O provision instala o MySQL, grava /etc/mysql/conf.d/lab.cnf com server_id, binlog ROW e GTID, reinicia o serviço e, se ROLE=source, cria o usuário repl.
  • Com as duas VMs no ar, você executa na réplica o CHANGE apontando para 192.168.56.11 e START REPLICA.
  • SHOW REPLICA STATUS e a comparação de gtid_executed validam o fluxo; inserir no source e ler na réplica é o teste de fumaça.
  • vagrant halt db02 + vagrant up db02 simula a queda de uma réplica; a replicação retoma sozinha do ponto guardado.

Na prática

  • Subir primeiro o source, validar o MySQL nele, e só depois subir a réplica — ordem importa no provision.
  • Manter um único provision.sh com if de papel em vez de dois scripts copiados — divergência entre scripts vira divergência entre nós.
  • Usar super_read_only=ON na réplica para impedir escrita acidental que gere GTID local.
  • Documentar os IPs e as credenciais no README do lab; IP fixo é contrato.
  • Ensaia halt/restart de cada nó com a replicação rodando antes de se declarar pronto.

Troubleshooting

SintomaRéplica não resolve ou não alcança o source.
CausaVMs em redes diferentes, ou provision rodou antes da rede subir.
AçãoDe dentro da réplica: ping -c2 192.168.56.11 e mysqladmin -h 192.168.56.11 -u repl -p ping. Se o ping falha, vagrant reload db02; se só o mysql falha, revisar usuário e bind-address no source.
Sintomaserver_id igual nos dois nós e a replicação recusa iniciar.
CausaVariável SERVER_ID não chegou ao provision de um dos nós.
AçãoEm cada VM: SELECT @@server_id; Se iguais, corrigir o Vagrantfile e vagrant provision. Não editar my.cnf à mão — corrigir a fonte.
SintomaApós vagrant destroy de um nó, o outro reclama de GTIDs desconhecidos.
CausaO nó destruído foi recriado vazio e o antigo UUID ainda aparece no conjunto do parceiro.
AçãoÉ esperado ao recriar do zero: reprovisionar a réplica a partir do source atual (dump com GTID) em vez de tentar reaproveitar coordenadas antigas.

SaltStack separa transporte e desejo: o master (portas 4505/4506) publica jobs e recebe retornos; o minion executa. A confiança começa com a troca de chaves — o minion gera um par e o master aceita com salt-key -A, identificando cada máquina pelo id. Como funciona

  • Você instala salt-master numa VM (ou no host) e salt-minion na VM alvo, apontando o minion para o master por master: <ip-ou-nome> em /etc/salt/minion.
  • O minion se apresenta; no master, salt-key -L mostra a chave pendente e salt-key -A -y <id> confere confiança.
  • Em /srv/salt/mysql/init.sls você declara pacote, /etc/mysql/conf.d/lab.cnf e serviço com watch — qualquer mudança no .cnf reinicia o MySQL sozinho.
  • O /srv/salt/top.sls associa base -> minion -> mysql; salt 'db*' state.apply (ou highstate) converge.
  • salt 'db*' service.status mysql e um mysql -e 'SELECT VERSION()' pelo minion provam o resultado; repetir o apply prova a idempotência.

Na prática

  • Fixar o id do minion igual ao hostname (db01) para o targeting por nome funcionar sem glob complicado.

Conceito

Pillar é o dado por minion que o master entrega sob demanda: cada minion vê só o seu. Você define mysql:role e mysql:server_id por id (db01 source/1, db02 replica/2) e o state lê esses valores via Jinja para renderizar o lab.cnf com o server_id correto e, na réplica, super_read_only. O mesmo state cria o banco labdb e — só no source — o usuário repl via mysql_user.present. A ligação da replicação (CHANGE + START) roda como um state cmd.run com unless que verifica se a réplica já está rodando, para o highstate continuar idempotente. O resultado é fleet como código: adicionar um db03 é uma linha no pillar, não um procedimento novo.

Como funciona

  • O /srv/pillar/top.sls entrega mysql.sls a db01 e db02; o mysql.sls define role e server_id por minion.
  • O template lab.cnf usa {{ pillar['mysql']['server_id'] }} e um bloco condicional que adiciona super_read_only só quando role == 'replica'.
  • O state mysql/replica.sls cria o usuário repl apenas no source (when por grain/pillar) e executa o CHANGE na réplica com unless checando Replica_SQL_Running.
  • salt 'db*' state.highstate converge os dois; salt 'db02' cmd.run com SHOW REPLICA STATUS valida.
  • Inserir no source e ler na réplica fecha o ciclo; salt 'db*' mysql.query substitui o ssh para as verificações de rotina.

Na prática

  • Manter pillar separado de states e fora do mesmo commit de senha real — usar pillar.example no git e o real só no master.
  • Todo cmd.run com comando de escrita precisa de unless ou onlyif — sem guarda, não é state, é script remoto.
  • Testar o template com salt 'db02' slsutil.renderer antes do highstate para ver o .cnf renderizado sem aplicar.
  • Rodar highstate por papel (salt -G ou salt 'db01') antes do tudo-junto para isolar erro de targeting.
  • Documentar a promoção de réplica como operação manual fora do highstate — failover automático não se improvisa em state.

Conceito

Um algoritmo é uma sequência finita de passos não ambíguos que transforma uma entrada numa saída. Finitude importa: um procedimento que nunca termina não é algoritmo, é bug. Não ambiguidade importa: 'verificar a réplica' não é passo executável, mas 'ler Seconds_Behind_Source e comparar com 60' é. A variável é uma caixa nomeada que guarda um valor com um tipo: inteiro (server_id), decimal (lag em segundos pode ser fracionário), texto (hostname) e lógico (verdadeiro/falso — réplica saudável ou não). O tipo decide quais operações fazem sentido: somar dois hostnames não existe, mas comparar dois lags sim. Pseudocódigo é o algoritmo escrito em português estruturado — o rascunho que você testa com a cabeça antes de gastar tempo com sintaxe de linguagem.

Como funciona

  • Todo algoritmo se descreve em três partes: ENTRADA (o que ele recebe — ex.: o valor de Seconds_Behind_Source), PROCESSAMENTO (o que ele faz — comparar com o limite) e SAÍDA (o que ele produz — 'OK' ou 'ALERTA').
  • Declarar uma variável é reservar a caixa e dizer o tipo: lag_segundos como inteiro-vindo-do-MySQL, limite como inteiro fixo em 60.
  • Operadores relacionais (>, <, =, diferente) comparam valores e devolvem um lógico; operadores lógicos (E, OU, NÃO) combinam lógicos entre si.
  • A precedência decide a ordem: aritmética antes de comparação, comparação antes de lógica — e parênteses passam por cima de tudo quando a intenção não está óbvia.
  • O pseudocódigo pronto vira o esqueleto do script final em qualquer linguagem: cada linha estruturada corresponde a 1–3 linhas de Bash ou Python.

Na prática

  • Antes de codar qualquer automação, escrever o bloco ENTRADA/PROCESSAMENTO/SAÍDA num comentário no topo do script.
  • Nomear variáveis pelo que guardam (lag_segundos, host_origem), nunca por x, aux ou temp — nome ruim esconde bug de lógica.
  • Uma variável, um conceito: se lag_segundos passa a guardar também mensagem de erro, o algoritmo quebrou — crie outra variável.
  • Testar o pseudocódigo com três valores concretos: o normal (lag 5), o limite (lag 60) e o absurdo (lag NULL quando a replicação está parada).
  • Guardar o pseudocódigo como comentário no script final: daqui a seis meses, é ele que explica o porquê.

Troubleshooting

SintomaO script roda sem erro mas decide errado (alerta quando não devia, ou vice-versa).
CausaBug de lógica, não de sintaxe: comparação invertida (usou < em vez de >) ou limite com unidade errada (milissegundos comparados como segundos).
AçãoVoltar ao pseudocódigo e executar à mão com os valores reais do incidente. Bug de lógica se caça no raciocínio, não no manual da linguagem.
SintomaErro de tipo: não consigo somar, comparar ou concatenar.
CausaVariável com tipo diferente do esperado — o clássico é número lido como texto ('60' em vez de 60) ou NULL onde se esperava número.
AçãoExplicitar a conversão logo na entrada (texto-para-inteiro) e tratar o NULL como caso separado antes de qualquer comparação.
SintomaO procedimento 'às vezes funciona', sem padrão aparente.
CausaPasso ambíguo que depende de estado externo: 'pegar o lag atual' muda entre duas leituras, ou a réplica avaliada não é sempre a mesma.
AçãoCongelar a entrada no início (ler uma vez, guardar em variável) e nomear exatamente qual instância está sendo avaliada.

Conceito

Qualquer algoritmo se constrói com três estruturas: SEQUÊNCIA (faça A, depois B), SELEÇÃO (se condição, faça A, senão faça B) e REPETIÇÃO (enquanto condição, repita A). A seleção tem duas formas: o SE/SENÃO para dois caminhos e a seleção múltipla (ESCOLHA/CASO) para vários valores de uma mesma variável — como o estado da réplica (Connecting, Yes, No). A repetição também tem duas formas: o PARA, quando você sabe quantas vezes repete (varrer as 3 réplicas), e o ENQUANTO, quando repete até uma condição mudar (tentar conectar até conseguir ou esgotar 5 tentativas). Curto-circuito é o avaliador preguiçoso do E/OU: em 'réplica existe E lag > 60', se a primeira parte é falsa a segunda nem é avaliada — o que evita erro ao consultar lag de réplica inexistente.

Como funciona

  • A sequência executa de cima para baixo; a ordem das linhas é o comportamento — trocar duas linhas pode trocar o resultado.
  • O SE avalia a condição uma vez e escolhe um caminho; SENÃO SE encadeia vários testes sobre o mesmo valor sem aninhar SE dentro de SE.
  • O PARA percorre uma faixa conhecida com contador (réplica 1 até 3) e termina sozinho; é o loop que não vira infinito.
  • O ENQUANTO testa antes de cada volta e precisa de algo dentro do corpo que aproxime o fim (incrementar tentativa, dormir 5s) — sem isso, loop infinito.
  • O curto-circuito ordena as condições da mais barata/segura para a mais cara/arriscada: primeiro 'réplica responde', depois 'lag > 60'.

Na prática

  • Preferir SENÃO SE encadeado a SE aninhado: cada nível de aninhamento dobra o custo de leitura do código.
  • Preferir PARA quando o conjunto é conhecido (lista de hosts, lista de bancos); reservar ENQUANTO para espera com condição de saída e limite de tentativas.
  • Todo ENQUANTO de espera precisa de dois freios: número máximo de voltas E pausa entre elas (sleep) — sem pausa vira ataque contra o próprio banco.
  • Ordenar condições aproveitando o curto-circuito: teste barato que elimina a maioria dos casos sempre primeiro.
  • Documentar a condição de saída do loop num comentário: 'sai quando conectar ou após 5 tentativas'.

Conceito

Decomposição é quebrar um problema grande em funções pequenas, cada uma com um nome que diz o que ela entrega: ler_lag(host), classificar(lag), alertar(host, status). A função recebe PARÂMETROS (a entrada), executa o corpo e devolve um RETORNO (a saída); o que nasce dentro dela (variável local) morre com ela — escopo local evita que duas partes do programa pisem na mesma variável. Teste de mesa é executar o algoritmo à mão, linha a linha, anotando o valor de cada variável numa tabela: é o debugger mais antigo do mundo e pega bug de lógica antes de qualquer execução. Custo (complexidade) conta quantas operações o algoritmo faz em função do tamanho da entrada: checar N réplicas uma vez é O(n) — dobra o fleet, dobra o tempo; comparar cada réplica com todas as outras é O(n²) — com 100 nós, 10 mil comparações.

Como funciona

  • Identifique os verbos do problema (ler, classificar, alertar) e vire cada um uma função com entrada e saída explícitas.
  • Parâmetros entram com cópia do valor: mudar o parâmetro dentro da função não muda a variável de quem chamou.
  • O RETORNO carrega o resultado para fora; função sem retorno útil serve só por efeito colateral (escrever log) — use com parcimônia.
  • O teste de mesa monta uma coluna por variável e uma linha por passo; ao final, o retorno anotado precisa bater com o esperado dos três casos (normal, limite, absurdo).
  • Para estimar custo, conte quantas vezes o corpo do loop mais interno executa: um loop sobre N é O(n); dois aninhados sobre N são O(n²).

Na prática

  • Regra dos 20: função que passa de ~20 linhas provavelmente esconde duas funções — quebre.
  • Uma função, um nível de abstração: ou ela decide (classificar) ou ela executa detalhe (conectar no socket) — misturar os dois dificulta teste.
  • Fazer o teste de mesa dos três casos antes de codar; se a mesa não fecha no papel, não fechará no servidor.
  • Em fleet, preferir O(n) com uma passada por host; desconfiar de loop dentro de loop cruzando inventário com métricas.
  • Medir tempo real com amostra pequena (3 hosts) e extrapolar: 3 hosts × 2s = 6s prevê ~200s para 100 hosts — número que decide entre script serial e paralelo.

Conceito

O Shell executa comandos e conecta o resultado deles: cada comando termina com um CÓDIGO DE SAÍDA (0 = sucesso, diferente de 0 = falha) guardado em $?. O IF do Bash não testa valores booleanos como outras linguagens — ele testa se um comando saiu com 0. Variáveis se criam por atribuição SEM espaços ao redor do = (LAG=5, nunca LAG = 5, que o Shell lê como três comandos). Quoting decide quando a variável expande: aspas duplas expandem ($HOST vira o valor), aspas simples não ('$HOST' continua literal), e $() captura a saída de um comando numa variável. Pipes (|) ligam a saída de um comando à entrada do outro, e redirecionamentos (>, >>, 2>) mandam saída para arquivos — com 2> separado para erros, porque misturar erro com dado corrompe relatório.

Como funciona

  • O shebang (#!/usr/bin/env bash) na primeira linha diz ao sistema qual interpretador executa o arquivo; chmod +x libera a execução direta.
  • VAR=valor guarda; $VAR ou ${VAR} lê — com chaves quando o nome cola em outro texto (${HOST}_backup).
  • Aspas duplas para quase tudo (preservam espaços e expandem variáveis); aspas simples para literais (regex, senhas com $ e ! que não podem expandir).
  • Comando entre $() vira texto: LAG=$(mysql -NBe 'SELECT ...') guarda o resultado da consulta na variável.
  • test/[ ] avalia condições de arquivo (-f existe?, -s não vazio?) e texto/número (-z vazio?, -eq igual numérico); [[ ]] é a versão moderna, sem pegadinhas de expansão.
  • Todo comando devolve exit code: encadear com && (só segue se deu 0) e || (só executa se falhou) cria fluxos de uma linha.

Na prática

  • Sempre citar variáveis: "$HOST", nunca $HOST solto — valor vazio ou com espaço quebra o comando de formas criativas.
  • Atribuição sem espaço: rever LAG = 5 toda vez que o erro for 'command not found' apontando para o nome da variável.
  • Usar [[ ]] em scripts novos; reservar [ ] para quando precisar de portabilidade POSIX explícita.
  • Comparar número com -eq/-gt e texto com =/!= — trocar um pelo outro é o bug mais comum do primeiro mês.
  • Separar stdout de stderr (2>erro.log) em todo script de cron: sem isso, erro e dado se misturam e o log mente.

Conceito

Função em Bash agrupa comandos sob um nome: recebe argumentos posicionais ($1 primeiro, $2 segundo, $@ todos) e devolve resultado de dois jeitos — texto pela saída padrão (capturado com $()) ou sucesso/falha pelo exit code (return 0/1). O chamador escolhe: valor com $(funcao), decisão com IF funcao. O modo estrito (set -euo pipefail) muda o contrato do script: -e aborta no primeiro comando com falha, -u aborta ao usar variável inexistente, -o pipefail reprova o pipe inteiro se qualquer etapa falhar (sem ele, mysqldump falhando mas gzip passando devolve 0 — backup vazio com cara de sucesso). trap captura sinais e erros para limpeza: remover arquivo temporário mesmo quando o script morre no meio.

Como funciona

  • FOR percorre lista fixa: for H in db01 db02 db03 — ou expansão $(cat hosts.txt) para inventário em arquivo.
  • WHILE lê linha a linha (while read -r) ou espera condição com contador e sleep — sempre com limite de voltas.
  • Função se define uma vez e se chama pelo nome; local declara variável interna para não vazar para o resto do script.
  • return devolve 0–255 (decisão); echo devolve texto (valor) — misturar os dois na mesma função confunde quem chama.

O with abre e fecha sozinho — arquivo aberto sem with e sem close vaza descritor até o script morrer. Exceção é o mecanismo de erro do Python: try tenta, except captura por tipo (FileNotFoundError, ValueError), else roda se deu certo e finally sempre limpa. A regra de ouro é capturar o tipo específico e deixar o resto subir: except genérico que engole tudo transforma falha de conexão em relatório vazio com cara de sucesso. logging substitui print em produção com NÍVEIS (DEBUG < INFO < WARNING < ERROR): você liga DEBUG para investigar e mantém INFO no dia a dia sem editar código.

Como funciona

  • O bloco else separa o caminho feliz do tratamento; finally fecha conexão do banco mesmo quando a query explode.

Conceito

O mysql-connector-python abre conexão TCP com o MySQL e devolve cursor para executar SQL e buscar linhas; dictionary=True entrega cada linha como dict (row['Variable_name']) em vez de tupla posicional — código que sobrevive a mudança na ordem das colunas. Query PARAMETRIZADA separa código de dado: o SQL leva placeholders %s e os valores vão num segundo argumento; o driver escapa e tipa — concatenar valor na string (f"... WHERE id = {id}") entrega a query à injection, sem exceção e sem 'é só lab'. Conexão é recurso escasso: abrir, usar e fechar (try/finally ou context manager), com connect_timeout para não pendurar o fleet quando um host cai. SHOW GLOBAL STATUS expõe centenas de contadores (Threads_connected, Questions, Uptime); coletar alguns por host em loop gera a série histórica que vira gráfico e alerta.

Como funciona

  • connect(host, user, password, connection_timeout) abre; cursor(dictionary=True) executa; fetchall/fetchone lê; close() devolve ao servidor.
  • cursor.execute("SELECT * FROM t WHERE id = %s", (id,)) parametriza — a tupla com vírgula mesmo para um único valor.
  • commit() confirma escrita; sem ele, o INSERT volta atrás no close — leitura não precisa de commit.
  • SHOW GLOBAL STATUS LIKE 'Threads_connected' filtra no servidor; o coletor guarda por host com timestamp único da rodada.
  • Falha num host (timeout) registra erro no relatório e segue para o próximo — um nó fora do ar não cancela a coleta do fleet.

Na prática

  • Placeholder %s sempre que houver valor variável no SQL — sem exceção, inclusive em scripts internos e labs.
  • Usuário de coleta com privilégio mínimo (SELECT em performance_schema + SHOW STATUS), nunca root no script.
  • Timeout curto (5s) por host e rodada com timestamp único: métricas comparáveis entre hosts.
  • Fechar cursor e conexão em finally — vazamento de conexão derruba o max_connections com o tempo.
  • Agendar a coleta no cron a cada 5 min gravando JSON datado; retenção de 7 dias igual ao backup.

Conceito

HCL é declarativa: você descreve o estado DESEJADO e o Terraform calcula o caminho — não há 'execute isto depois daquilo', há dependências inferidas das referências entre recursos. A lógica mora nas EXPRESSÕES: variáveis tipadas (string, number, bool, list, map, object) com validation que rejeita valor ruim no plan, locals para valores derivados (nomes padronizados), o ternário cond ? a : b para liga/desliga (backup ligado só em produção) e as funções (length, merge, join, format) para transformar. Repetição tem duas formas com consequência operacional: count cria N cópias indexadas por número (remover o item 0 renumera tudo e recria), for_each cria um mapa indexado por chave estável (remover db03 afeta só db03). Blocos dynamic geram sub-blocos repetidos (várias regras de SG) a partir de uma lista.

Como funciona

  • variable declara tipo, default e bloco validation com condition e error_message — o plan falha cedo com mensagem sua, não com erro críptico do provider.
  • locals derivam o que se repete: nome = "${var.projeto}-${var.ambiente}" usado em todos os recursos sem divergência.
  • O ternário decide valores: backup_retention_period = var.prod ? 7 : 0 — um .tfvars separa lab de produção.
  • for_each = toset(var.replicas) cria uma instância por chave; each.key identifica; remover um elemento do set destrói só aquele recurso.
  • dynamic "ingress" com for_each gera N regras de SG a partir de var.portas_liberadas — sem copiar bloco.
  • terraform validate + fmt -check no CI barram sintaxe quebrada e formatação divergente antes do plan.

Na prática

  • for_each como default para qualquer coleção nomeada (réplicas, bancos, usuários); count só para N idênticos descartáveis.
  • validation em toda variável que aceita conjunto fechado (ambiente em [lab, prod], engine em versão fixada).
  • Um .tfvars por ambiente (lab.tfvars, prod.tfvars) — o mesmo código, comportamentos diferentes, sem IF no recurso.
  • Outputs para tudo que outro módulo ou humano precisa (endpoint, porta) — nada de copiar valor do console.
  • plan -out + apply do arquivo em produção: o que foi revisado é o que aplica, sem deriva entre leitura e execução.

Conceito

O Ansible executa um PLAYBOOK (YAML) contra um INVENTÁRIO: cada PLAY mira um grupo de hosts e roda TASKS em ordem — módulos idempotentes (apt, copy, template, service, mysql_user) que convergem em vez de executar cegamente. A lógica usa as mesmas três estruturas do módulo 05, traduzidas: when é o SE (executa a task só se a condição), loop é o PARA (repete a task por item, com item como variável) e register é a atribuição (guarda o resultado — changed, stdout — para o próximo when). O Jinja2 ({{ var }}, {% if %}, filtros como | default e | join) renderiza arquivos e condicionais; handlers são tasks que só disparam no fim e uma única vez quando notificadas (restart do MySQL só se o .cnf mudou). Check mode (--check) é o dry-run: mostra o que mudaria sem mudar.

Como funciona

  • O inventário (hosts.ini ou YAML) agrupa: [source] db01, [replica] db02 db03 — o play mira o grupo, não IPs soltos.
  • Facts (ansible_facts) expõem SO, memória e IPs do host; when: ansible_os_family == 'Debian' adapta a task por plataforma.
  • register guarda o retorno; when: resultado.changed decide a próxima task — encadeamento sem shell.
  • template: copia .cnf.j2 renderizado por host (server_id por inventory_hostname) e notify: restart mysql.
  • O handler restart mysql roda uma vez no fim do play e só se notificado — dez tasks mudando config geram um restart, não dez.
  • ansible-vault criptografa senhas em vars; --check --diff valida antes, mostrando linha a linha o que mudaria.

Na prática

  • Tudo em roles (mysql/{tasks,handlers,templates,defaults}) quando passar de um playbook — playbook gigante vira monolito.
  • when com condição legível e comentada; condição complexa vira variável em vars (ex.: eh_replica) testável.
  • loop com lista nomeada em vez de with_items legado; loop_control.label para log legível por item.
  • Idempotência verificável: rodar o playbook duas vezes, a segunda com changed=0 — igual ao teste do Salt.
  • Segredos só via vault; nunca senha em vars aberto, nunca -e na linha de comando em host compartilhado.

Troubleshooting

SintomaTask diz changed em toda execução, nunca converge.
CausaMódulo sem idempotência real (command/shell em vez do módulo próprio) ou template renderizando diferente a cada run (timestamp, ordem de dict).
AçãoTrocar command por módulo nativo (mysql_user, template, lineinfile); estabilizar o template (ordenar com | sort) até changed=0 na segunda run.
Sintomawhen não filtra e a task roda onde não devia (ou o inverso).
CausaComparação de tipos (string 'true' vs booleano) ou variável indefinida avaliada como falsa silenciosa.
AçãoDebugar com - debug: var=nome_variavel antes do when; forçar tipo com | bool e default com | default(false).
SintomaHandler não reiniciou o MySQL após mudança de config.
Causanotify com nome diferente do handler (typo com hífen vs underscore) — o Ansible não avisa, só não dispara.
AçãoPadronizar nomes e conferir com --check: handlers aparecem como 'notified' no resumo; nome errado nunca aparece.
